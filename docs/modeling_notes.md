# Phase 5 - Modeling Notes

## Purpose

Phase 5 turns the reconciled relational layer into a dimensional design.

The reconciled layer explains how the sources were cleaned and integrated. The warehouse layer explains how the same data will be queried through OLAP operations.

## Conceptual Grain

The main fact is `dw.fact_trip`.

Grain: one accepted Citi Bike ride from `reconciled.trip`.

Every row represents one ride identified by `ride_id`. The fact keeps both start and end roles for date, time, station, and geography because most analyses compare demand origin, destination, and flow.

The performance aggregate is `dw.fact_station_day_hour`.

Grain: one station, one calendar day, and one start hour.

This aggregate is designed for live demo queries where scanning the ride-level fact would be slower or visually noisy.

The aggregate fact has a dedicated conceptual diagram in `diagrams/phase5_fact_station_day_hour_dfm.drawio`, parallel to the main ride-level DFM.

## Measures

`fact_trip` contains additive or semi-additive measures that support OLAP aggregation:

- `trip_count`: always 1.
- `duration_seconds` and `duration_minutes`.
- `approximate_distance_km`.
- `night_trip_count`: 1 for trips starting from 20:00 to 05:59, else 0.
- `member_trip_count` and `casual_trip_count`.
- Flow contribution indicators:
  - `same_station_trip_count`
  - `within_nta_trip_count`
  - `cross_nta_same_borough_trip_count`
  - `cross_borough_trip_count`
  - `outside_or_unknown_trip_count`

The fact also keeps `flow_direction` as a degenerate dimension because it is a low-cardinality trip classification derived during reconciliation.

## Dimensions And Hierarchies

### Time

Physical table: `dw.dim_time`

Hierarchy:

`hour -> part_of_day -> day_night_class`

The role-playing keys in `fact_trip` are `start_time_key` and `end_time_key`.

### Date

Physical table: `dw.dim_date`

Hierarchy:

`date -> week -> month -> quarter -> season -> year`

The role-playing keys in `fact_trip` are `start_date_key` and `end_date_key`.

### Calendar Event

Physical table: `dw.dim_calendar_event`

Hierarchy:

`date -> holiday_window -> long_weekend_flag -> holiday_type -> holiday_name`

This dimension is date-scoped because holiday eve, post-holiday, bridge day, and long-weekend semantics depend on the exact date. It is linked to the trip start date in `fact_trip`.

### Weather

Physical table: `dw.dim_weather`

Hierarchy:

`weather_day -> condition_class -> severity_label`

Weather is linked to trip start date. The source is daily NOAA Central Park weather, so weather describes the demand context at the beginning of each ride.

### Geography

Physical table: `dw.dim_geography`

Hierarchy:

`station -> NTA -> CDTA/community district -> borough -> city`

`dw.dim_station` references `dw.dim_geography`, and `fact_trip` also keeps start and end geography keys for direct origin/destination roll-ups.

### Station

Physical table: `dw.dim_station`

Hierarchy:

`station -> assigned NTA -> borough -> city`

The role-playing keys in `fact_trip` are `start_station_key` and `end_station_key`.

### User And Rideable Type

Physical tables:

- `dw.dim_user_type`
- `dw.dim_rideable_type`

These are compact descriptive dimensions used for slicing member/casual behavior and classic/electric bike behavior.

## Star/Snowflake Choice

The warehouse uses a hybrid star/snowflake schema:

- The ride fact remains connected directly to the main dimensions for simple OLAP and readable DBeaver demos.
- `dim_station` references `dim_geography`, creating a controlled snowflake edge for the strongest real hierarchy.
- `dim_geography` is denormalized at NTA level instead of splitting NTA, CDTA, borough, and city into separate tables. The geography table is small, so extra snowflake tables would add joins without improving query value.
- Date and calendar event are separated because date hierarchy and public-event semantics answer different analytical questions.

This design keeps the schema easy to defend: it shows non-trivial hierarchies without making the physical model hard to browse during the live demo.

## Controlled Unknown Rows

Phase 6 population scripts should insert controlled key `0` rows for dimensions before loading facts.

Expected unknown handling:

- Unknown or outside-NYC geography should resolve to a controlled geography row.
- Missing or unmapped station metadata should resolve to a controlled station row.
- Weather, calendar event, user type, and rideable type should also have controlled unknown rows for defensive loading.

The DDL uses `GENERATED BY DEFAULT AS IDENTITY` so population scripts can explicitly insert key `0`.
